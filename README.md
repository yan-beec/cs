# ICS 智能客服系统 · V1 阶段总结

ICS 是基于 Chatwoot 的智能客服系统，面向多业务渠道提供自动问答、人工接待衔接、客服桌面提醒和知识内容管理。

截至 **2026 年 10 月 16 日，智能客服模块 V1 的阶段性功能已完成**，已形成“客户咨询 → AI 应答 → 按需转人工 → 客服接待 → 结束本轮咨询”的业务流程。对话归档首版现包含独立数据库、原始事件接收、异步解析，以及后台的用户历史、轮次、坐席和评价查询；模型质检为后续开发方向。

本文记录当前软件的功能、使用方式与运行维护入口。具体功能是否启用，以部署环境的配置为准。

## 一、系统组成

| 组成部分 | 当前作用 |
| --- | --- |
| 客户端客服页面 | 承载 Chatwoot Website Widget，可用于网页及 APP WebView 客服入口 |
| Chatwoot 客服工作台 | 管理客户会话、座席在线状态、人工回复、会话分配及解决状态 |
| ICS 智能客服服务 | 接收消息，执行 FAQ / 知识库问答，控制咨询轮次与转人工流程 |
| ICS 管理后台 | 按渠道维护知识库和 FAQ，执行内容更新，查看运行日志 |
| Windows 提醒程序与浏览器插件 | 接收转人工提醒、播放提示音，并打开对应客户会话 |
| 对话归档模块 | 独立采集与解析；后台按用户、轮次、坐席、时间和评价查阅，保留原始消息版本 |

## 二、V1 已具备的功能

### 1. 多渠道独立接待

目前配置了四个业务渠道：

| 渠道 | 渠道标识 | 业务资料目录 |
| --- | --- | --- |
| 兴聊 | `xingliao` | `database/channel_xingliao/` |
| 言聊 | `yanliao` | `database/channel_yanliao/` |
| 星盈通 | `xingyingtong` | `database/channel_xingyingtong/` |
| 微信 | `wechat` | `database/channel_wechat/` |

各渠道共用服务程序，分别维护 FAQ 数据表、知识库集合和回复提示词；对话记忆按渠道和会话隔离。机器人根据 Chatwoot 账户与收件箱（Inbox）识别渠道，管理后台提供对应的渠道入口。

渠道映射集中保存在 [database/channels.json](database/channels.json)。新增或调整收件箱时，应更新对应绑定并重启服务；业务资料上传到所属渠道。

### 2. FAQ 优先、知识库补充的自动问答

普通文本咨询按以下顺序处理：

```text
客户发送问题
  → 在所属渠道的 FAQ 中匹配
  → 命中：直接返回标准答案
  → 未命中：意图识别 → 知识库检索 → 可选精排 → 云端大模型生成回复
  → 将答案发回原 Chatwoot 会话
```

- **FAQ 标准问答**：从 Excel 导入，通过 BM25 匹配常见问题，命中后直接使用维护好的答案。
- **知识库问答**：使用本地 BGE-M3 和 ChromaDB 检索业务资料，结合渠道提示词、意图结果与对话上下文生成回答。
- **可选精排**：通过 `RAG_RERANKER_ENABLED` 控制是否加载精排模型。当前配置模板设为 `false`，关闭时使用向量召回的前 5 条结果。
- **主备模型切换**：主模型失败、超时或返回空内容时，可在剩余请求时间内使用已配置的备用模型。
- **消息展示**：支持文字、链接及答案中的 Markdown 图片，兼容已有答案里的 HTML 图片标签转换。
- **特殊消息处理**：纯表情消息使用默认提示；客户发送图片或视频时进入转人工判断，交由人工处理。

知识库维护支持文本、Markdown、PDF、Word 文档及图片等资料，包含文档分块、图片文字识别和向量库构建能力。

### 3. 多轮对话与咨询轮次管理

- 同一轮咨询可使用 PostgreSQL 中保存的 AI 对话上下文，支持连续追问。
- Chatwoot 会话标记为“已解决”后，本轮咨询结束；客户再次发消息时重新进入 AI 接待，并使用新的上下文。
- 客户连续 **6 小时**未发送新消息，下一条消息开启新轮次；该时长可通过 `CHATWOOT_SESSION_IDLE_TIMEOUT_SECONDS` 调整。
- 6 小时边界用于切换上下文，不会自动结束人工接待或将会话标记为已解决。
- 新旧轮次隔离，已结束或已切换轮次的旧答案在发送前会再次检查，避免迟到回复干扰当前咨询。
- AI 记忆支持按保留天数清理；当前模板为 15 天。完整客户聊天记录仍由 Chatwoot 管理。

### 4. 转人工与座席分配

客户明确提出“人工”“转人工”，或发送图片、视频附件时，系统进入人工接管流程。

- 检查当前会话所属 Inbox 的座席，按配置进一步限定团队或指定客服。
- 仅向处于 `online` 状态、且未达到接待容量的座席分配；优先分配给同一 Chatwoot 会话最近一次成功分配的人工座席。
- 原座席离线、忙碌、满额或不符合当前 Inbox/团队/指定客服范围时，按现有轮询规则选择其他可用座席；没有可靠历史记录时也走轮询。
- 历史优先依据为 ICS 每轮首次成功分配记录，后续人工改派不覆盖；中间的纯 AI 轮次不清除偏好，新建另一条 Chatwoot 会话时不继承。
- 每位座席默认最多承接 **5 个处于 open 状态的人工会话**，可通过 `CHATWOOT_HANDOFF_MAX_ACTIVE_CONVERSATIONS` 调整。
- 成功接管后，打开人工会话、分配座席、添加转人工标签和私有备注，并停止当前会话的 AI 自动回复。
- 没有可用座席时向客户提示当前无法接入人工，保留 AI 接待能力。
- 普通 AI 接待期间使用 `pending` 状态；人工接管后使用 `open` 状态。
- 联系人静音与转人工控制联动，避免被静音的联系人通过转人工重新打开会话；静音默认持续 24 小时后自动解除。

人工分配在当前 Inbox 内完成。客服结束处理时，应在 Chatwoot 中将会话标记为“已解决”，以结束本轮接待。

### 5. Windows 客服桌面提醒

提醒功能由 ICS 服务端、Windows 桌面程序和 Chrome / Edge 浏览器插件共同完成。

- 成功转人工后，向被分配座席的电脑发送提醒。
- 显示置顶弹窗并播放提示音，可查看会话编号、客户姓名、收件箱名称及消息摘要。
- 点击“打开 Chatwoot 工作台”，通过浏览器插件进入对应会话，并优先复用已登录标签页。
- 每条提醒需单独点击“确认收到”；仅打开工作台不会确认提醒，未确认时会继续提示。
- 会话被解决或改派后，提醒随状态同步撤销或转给新座席。
- 支持试验提醒、共享电脑切换值班席位、本机设备记忆和系统托盘驻留。
- 提醒程序使用独立插件账号登录；接待客户仍使用客服本人的 Chatwoot 账号。

### 6. 管理后台与内容维护

管理后台入口为 `/admin`，当前页面名称为“零新智能客服”。后台支持管理员登录认证，并按渠道提供：

- 知识库文件列表、上传、预览、下载与删除。
- FAQ Excel 上传、在线浏览与下载。
- 提交“更新知识库”任务，执行资料解析与向量库重建。
- 提交“更新 FAQ 数据库”任务，替换渠道 FAQ 并刷新服务内存中的匹配索引。
- 查看更新任务的提交结果，并通过集中日志检查各渠道的处理过程与完成情况。

管理员账号通过 `ADMIN_USERNAME` 配置，首次初始化密码通过 `ADMIN_INITIAL_PASSWORD` 配置。管理员记录创建后，修改初始密码配置不会覆盖数据库中已有的密码。

### 7. 服务评价与运行保障

| 功能 | 当前行为 |
| --- | --- |
| 按轮次满意度评价 | 可选启用；每轮咨询解决后发送独立原生评价卡，评分进入 Chatwoot 满意度报告。默认关闭，需配置并部署配套 Chatwoot 补丁 |
| Webhook 校验与去重 | 校验消息来源签名，记录事件幂等状态，避免重复处理 |
| 后台消息处理 | 接收后入队处理，同一会话串行执行，失败按策略重试 |
| 故障兜底 | 对模型、检索及超时异常提供兜底提示，并记录处理结果 |
| 运行日志 | 提供后台日志视图及 `log/` 下的轮转日志文件 |
| 部署与升级 | 提供 Docker Compose、服务器代码同步、归档库迁移验证及统一发布脚本 |

## 三、日常操作

### 1. 客户咨询

1. 从业务网页或 APP 的客服入口进入对应渠道的聊天页面。
2. 输入文字问题，系统自动选择标准答案或知识库回答；同一轮内可以继续追问。
3. 需要人工时发送“转人工”，等待可用客服接入。图片和视频咨询同样会触发人工接管判断。
4. 本轮结束后，仍可在原窗口发起下一轮咨询。

客服页面支持匿名访问，也支持通过业务后端提供的用户身份及签名接入登录态、识别用户和关联历史会话。正式身份接入需由业务后端验证登录态并生成签名。

### 2. 客服值班与人工接待

1. 登录 Chatwoot 工作台，确认本人属于需要接待的 Inbox，并将接待状态设为在线。
2. 启动 Windows 提醒程序，使用插件账号登录，选择本人的值班席位。
3. 确认“ICS 已连接”和“浏览器插件已连接”，通过“测试提醒”检查连接。
4. 收到真实提醒后，点击“打开 Chatwoot 工作台”进入对应客户会话，并点击“确认收到”。
5. 在 Chatwoot 中回复客户，处理完成后将会话标记为“已解决”。“确认收到”仅结束提醒。
6. 交接班时切换 Chatwoot 登录账号，并在提醒程序中切换为接班人的席位。

提醒程序目前需要每天手动启动。关闭主窗口后会继续在托盘运行；点击“退出程序”才会停止提醒。

安装、浏览器授权与常见问题见 [客服提醒安装与使用说明](reminder/docs/客服安装与使用说明.md)；服务端配置与客户端打包见 [提醒模块说明](reminder/README.md)。

### 3. 管理员更新 FAQ

1. 登录 `/admin`，选择要维护的业务渠道。
2. 下载当前 FAQ Excel，修改或补充问答后上传 `.xlsx` 文件。
3. 点击“更新 FAQ 数据库”，确认本次全量更新。
4. 结合系统日志确认任务成功，在该渠道发送代表性问题检查回答。

FAQ 工作簿需包含以下列：

```text
question    answer    need_human    enabled
```

上传文件名不限，校验通过后自动保存为所属渠道的 `最新问答对.xlsx`（如显式配置了自定义路径，则使用该路径，与更新逻辑一致）。上传时会检查实际 Excel 内容和 FAQ 导入格式；非 `.xlsx`、损坏文件或无效问答表会报错并保留原文件。旧版 `.xls` 请先另存为 `.xlsx`。

上传文件与更新数据库是两个步骤。FAQ 更新会全量替换对应渠道的数据，操作前保留原工作簿。

### 4. 管理员更新知识库

1. 在后台进入目标渠道，上传新资料，或删除已失效资料。
2. 点击“更新知识库”，提交解析及向量库重建任务。
3. 等待任务成功，结合系统日志检查结果。
4. 从客户入口测试受影响的业务问题，核对回答内容。

文件上传或删除后，需要执行知识库更新才会改变检索内容。渠道回复提示词保存在各资料目录的 `prompt_*.md` 文件中，通过文件维护；文件调整后，后续生成回复时会读取新内容。

## 四、运行与部署

### 1. 运行前准备

- 已部署的 Chatwoot，以及对应账户、Inbox、AgentBot 和访问凭据。
- Python 3.10 运行环境，或 Docker 与 Docker Compose。
- PostgreSQL 数据库、各渠道业务资料和本地检索模型。
- 可用的云端大模型服务。

首次配置时，将 [.env.example](.env.example) 复制为根目录 `.env`，填写目标环境配置。主要配置项如下：

| 配置分组 | 内容 |
| --- | --- |
| `POSTGRES_*` | 机器人业务数据库连接 |
| `ADMIN_USERNAME`、`ADMIN_INITIAL_PASSWORD`、`ADMIN_JWT_SECRET` | 后台管理员与登录签名配置 |
| `LLM_MODEL`、`LLM_MODEL_PROVIDER`、`LLM_API_KEY`、`LLM_BASE_URL` | 主模型；对应的 `*2` 配置用于备用模型 |
| `CHATWOOT_*` | Chatwoot API、AgentBot、自动回复、身份接入、人工接管及评价 |
| `RAG_*`、`KNOWLEDGE_BASE_*` | 检索、精排、意图模型、知识库与记忆管理 |
| `REMINDER_*` | 提醒开关、插件独立登录和设备限制 |
| `ARCHIVE_*` | 独立归档库与原始事件接收服务 |

`CHATWOOT_BASE_URL` 用于服务端访问 Chatwoot，`CHATWOOT_PUBLIC_BASE_URL` 用于浏览器访问。自动回复、桌面提醒和按轮次评价均有独立开关，需按实际使用场景启用；示例文件中的密码和密钥需替换为实际配置。

本地模型文件不包含在 Git 仓库中。常用模型目录为：

```text
models/
├── bge-m3/                                  向量检索模型
├── bge-reranker-v2-m3/                      启用精排时使用
├── intent_classifier_bert/                  运行时意图分类模型
└── google-bert--bert-base-chinese/          重新训练意图模型时使用
    └── snapshots/master/
```

### 2. 本地启动

在项目根目录准备好 `.env`、模型和业务资料后，可通过 Compose 启动：

```powershell
docker compose up -d --build
```

默认自动加载 `docker-compose.override.yml`，挂载本地业务代码并启用热重载。首次运行还需在管理后台为各渠道导入 FAQ、执行知识库更新。

也可直接运行 Python 服务：

```powershell
python -m pip install -r requirements.txt
docker compose up -d postgres
python -m ics_agent.app.serve --host 127.0.0.1 --port 3001 --reload
```

直接运行时，PostgreSQL 连接应指向宿主机；当前示例的 `POSTGRES_PORT` 与 `POSTGRES_HOST_PORT` 均为 `5433`。Compose 中的应用则使用 `postgres:5432`。

| 入口 | 本地默认地址 | 用途 |
| --- | --- | --- |
| 管理后台 | `http://127.0.0.1:3001/admin` | 资料维护和日志查看 |
| 健康检查 | `http://127.0.0.1:3001/health` | 检查应用 HTTP 服务是否响应 |
| 通用客服页面 | `http://127.0.0.1:3001/support-chat` | 随标准镜像提供的客服承载页，需配置渠道 Widget |
| Chatwoot 工作台 | 实际部署的 Chatwoot 地址 | 人工接待、座席和会话管理 |

机器人接收地址为 `POST /webhooks/chatwoot`，推荐使用 AgentBot Webhook 并配置对应签名 Secret。将 AgentBot 绑定到目标 Inbox，并启用 `CHATWOOT_AUTO_REPLY_ENABLED` 后，机器人才能实际发送自动回复；轮次结束功能还需要会话状态事件正常送达。

服务器采用后端专用镜像时，客户入口使用已独立部署的前端页面。

### 3. 日常更新与检查

本地 Compose 常用操作：

```powershell
# 查看服务状态
docker compose ps

# 修改依赖或构建文件后，重新构建应用
docker compose up -d --build ics-agent

# 修改 .env 后，重新创建容器以读取新配置
docker compose up -d --force-recreate ics-agent
```

服务器使用统一发布入口，完成代码同步、归档数据库迁移与验证，再构建并更新应用：

```bash
bash /opt/cs-src/deploy/server/release.sh --source /opt/cs-src --target /opt/cs
```

启用可选归档接收服务时，在发布命令中增加 `--with-receiver`，并按消息接收说明配置独立账户级 Webhook。

更新后应检查后台登录、各渠道 FAQ / 知识库回答、转人工、提醒及“已解决后重新咨询”。`/health` 正常仅表示应用可响应，业务可用性仍需通过上述流程核对。

## 五、对话归档与质检的当前进度

当前仓库已包含对话归档查询首版，后续将在此基础上加入模型质检：

| 已实现内容 | 当前范围 |
| --- | --- |
| 独立归档数据库 | 与机器人业务库分开存储，使用独立连接池及分级账号权限 |
| 数据库迁移与验证 | 已纳入服务器统一发布流程，验证原始证据追加及只读权限 |
| 原始 Webhook 接收 | `POST /quality/webhooks/chatwoot`，默认端口 `3010`，使用专用账户级 Webhook 签名 |
| 原始事件持久化 | 不按机器人入站条件过滤，保存收到的客户、人工、机器人及私密消息等事件原始载荷 |
| 持久化待处理任务 | 原始事件与处理任务在同一事务中写入，提交后确认接收；重复投递去重 |

**采集服务继续只写入原始事件和持久化任务。** 新增独立解析工作进程生成消息、会话、评价快照及可重建的查询索引；ICS 管理后台增加“对话归档”，可按用户或轮次浏览、筛选接待类型和坐席，并查看完整历史、编辑删除版本和待关联评价。后台使用独立只读连接池，默认关闭；启用需应用 `002_query` 迁移、启动工作进程并开启查询开关。附件文件独立复制、源端历史补录及模型质检尚未完成，源端未投递的消息不能仅靠已归档数据恢复。

配置和启用见 [归档查询首版说明](quality/query/README.md)，其他模块说明见 [归档与质检模块](quality/README.md) 和 [消息接收](quality/capture/README.md)。

### 客服状态监管

管理后台左侧“系统管理”提供独立“客服状态监管”页面（`/admin#presence`），查看当前 Chatwoot 坐席状态及每日统计；选择日期和坐席可查看北京时间 00:00–24:00 的全天分钟时间轴。每分钟区间开始包含、结束不包含；未知状态、缺采样、未监控、已过期和未来时间分别展示，今日尚未结束的分钟不计入已完成统计。时间轴查询沿用状态采样表，保留期清理由下述迁移提供。

坐席在线、忙碌、离线状态采用每分钟采样，默认关闭。先按发布流程依次应用 `004_agent_presence`、`005_presence_retention`、`006_presence_retention_state` 迁移，在 `.env` 配置独立随机 `ARCHIVE_PRESENCE_PASSWORD`、`ARCHIVE_PRESENCE_USER=archive_presence`，再设置 `ARCHIVE_PRESENCE_ENABLED=true` 并重新创建 ICS 容器。采集使用与查询相同的归档库和来源配置，独立连接池固定最多 1 个连接；`ARCHIVE_PRESENCE_MAX_AGENTS` 默认 100，允许范围为 1–200。采样周期固定为 60 秒。

采集随当前单进程 ICS 运行，部署保持单实例采集。每天的状态时长根据分钟观测计算，属于采样统计；服务停机、连接失败造成的缺采样分钟不补造为离线，也不沿用上一分钟状态。采样区间用于核对观测，不代表秒级上下线时间或精确考勤，不能单独据此认定实际工时、迟到、早退或缺勤。原始聊天归档不受状态采集影响，启用前的状态历史无法由采样恢复。详见[客服状态监管说明](quality/query/README.md#客服状态监管)。

状态历史按数据库保存的实际采样时间保留 **至少45天（45×24小时）**，每天北京时间 **04:00** 以“当天04:00减45天”为界分批清理全部更早记录。数据库持久保存每日进度和200批限额，重启不重置预算，漏清次日继续；大量积压按限额分日消化。最早日期04:00前的分钟明确标记已过期，不当作缺采样或离线。此清理仅针对客服状态历史，不清理原始聊天归档。服务器逐步操作见[归档功能更新文档](docs/archive-feature-update.md)。

## 六、技术组成与项目目录

当前后端采用 **Python 3.10 + FastAPI**；问答流程使用 LangGraph，FAQ 使用 BM25，知识检索使用 BGE-M3 + ChromaDB，意图分类使用本地中文 BERT，回答生成通过云端模型完成。PostgreSQL 保存机器人业务状态和对话记忆；归档数据使用独立 PostgreSQL 服务。

```text
ics_agent/                 智能客服主服务、管理后台、FAQ、RAG、渠道与模型调用
reminder/                  提醒后端、Windows 客户端、浏览器插件与安装说明
quality/                   对话归档、事件接收及后续质检模块
statistics/                统计报表、时间趋势及坐席细化（共用归档数据）
knowledge_base_in/         文档解析、分块、向量构建与生成产物
database/                  渠道配置、FAQ、知识库、提示词与训练资料
models/                    本地模型文件
deploy/                    服务器部署、发布、归档库及 Chatwoot 配套配置
docs/                      部署与专项功能说明
tests/                     智能客服相关测试
log/                       运行日志
```

当前机器人消息处理使用单应用进程、内存队列和进程内会话锁，部署时保持单实例运行；尚未完成请求在进程异常退出后不能依靠该队列自动恢复。归档采集使用独立的数据库任务表，两者承担不同职责。
