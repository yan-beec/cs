## 一、背景与目标

生产环境运行一段时间后，运营与质检侧反馈集中在三类问题：

1. **转人工被反复刷**：部分用户在短时间内多次发送“转人工”，挤占坐席资源，现有逻辑只有“有空闲坐席就转、没有就提示繁忙”两种结果，缺少针对高频用户的门槛。
2. **数据量增长后统计与导出不可用**：统计报表拉长时间范围后报“统计查询暂不可用”，Excel 导出提示笼统，平均响应、咨询总时长等指标出现明显不合理的数值。
3. **质检与归档查阅效率低**：筛选结果与点开后的内容不一致，聊天记录阅读区过宽、颜色区分度低，质检保存、时间筛选等高频操作控件偏小，列表无法直接跳页，导出只有 Excel 不便离线查阅。

本需求包共 13 项，目标是：在**不改变智能客服主链路行为**（AI 应答、坐席分配、webhook 处理）的前提下，增加转人工门槛、统一统计口径、保证大数据量下系统“可以慢、不能崩”，并提升质检与归档的操作效率。

### 1.2 名词说明

| 名词 | 含义 |
| --- | --- |
| 用户 | Chatwoot 同一工作区（account）下的同一联系人（contact）。同一用户多次咨询会产生多个 Chatwoot 会话 |
| 轮次 | 一次咨询。一个 Chatwoot 会话被“解决”后客户再来，形成同一会话内的下一轮 |
| 转人工请求 | 客户发送明确的“转人工/人工”类表达，或发送图片/视频触发的自动转人工（与现有触发规则一致） |
| 成功转人工 | 一次转人工请求最终由 ICS 预留并分配到坐席、会话转入人工接待。坐席繁忙、黑名单拒接、进入排队、功能关闭等未分配到坐席的结果都不算成功 |
| 主责坐席 | 每轮唯一的考核坐席：ICS 已确认分配的坐席；没有分配记录时为转人工后第一个发出有效公开回复的坐席 |
| 协助轮次 | 同一轮中，主责坐席以外的坐席在转人工后发出过有效公开回复（多见于交班） |
| 有效消息 | 公开的非空文字或附件；排除私密备注、评价卡、系统活动、已删除/空白消息及触发转人工的那条消息本身 |
| 纯 AI 接待 / 人工介入 | 归档的接待分类：全程只有 AI 应答为纯 AI；发生过转人工并有人工参与为人工介入 |

## 二、R1 渐进式转人工门槛（动态排队）

### 2.1 当前情况

- 客户发送转人工请求后，ICS 依次判断：功能开关 → 是否有在线空闲坐席 → 是否被拉黑 → 预留并分配坐席。有坐席即转接，无坐席则回复“当前人工坐席繁忙……请稍后再次尝试「转人工」”。
- 系统**不记录同一用户的转人工次数**，会话控制表只按会话保存当前状态。用户可以无限次、无间隔地发起转人工，高频用户每次都能直接进入人工队列。
- 没有“排队”概念，客户看不到等待进度，只能反复发送“转人工”。

### 2.2 设计方案

#### 2.2.1 计次规则

| 规则 | 说明 |
| --- | --- |
| 计次对象 | 用户（account_id + contact_id）。无法识别联系人的请求不计次、不排队，按原流程处理 |
| 计入一次的条件 | 只有**成功转人工**才计入一次（见名词约定），在分配坐席成功的时刻记录。显式关键词或图片/视频触发的请求，只要转接成功都计入；持有兑现机会、兑现时转接成功的也计入 |
| 不计次的情况 | 只发起请求、没有转接成功的一律不计：① 进入排队，或排队中再次请求；② 坐席繁忙、黑名单拒接（包括持有兑现机会时被拒的情况）；③ 同一条消息的 webhook 重试（按消息 ID 去重，同一条消息最多计 1 次）；④ 已处于人工接待中的消息；⑤ 门槛模块故障放行后转接成功、但次数更新失败的（记告警，不补计） |
| 第 N 次的判定 | 收到新请求时，用日计数/周计数**已成功**的次数加 1 判定档位，即“如果本次成功，将是第 N 次”。例如近 24 小时已成功转人工 4 次，第 5 次请求进入排队；发起多少次请求、被拒多少次都不影响 N |
| 日计数 | **滚动 24 小时**：以收到请求的当前时刻往前 24 小时内（成功时间晚于“当前时刻 − 24 小时”）的成功转人工次数。不在固定时刻清零，每次成功满 24 小时后单独过期。例：昨天 15:00 成功的一次，今天 15:00 之后不再计入 |
| 周计数 | 本周五 09:00 起的成功转人工次数，**每周五 09:00 清零** |
| 时间与互不影响 | 均按北京时间；日计数滚动过期、周计数周五 09:00 清零，两者各自计算、互不影响（周五 09:00 只清周计数，不影响近 24 小时的日计数） |

#### 2.2.2 排队人数

初始排队人数 = 日档位人数 + 每周附加人数。下表为默认值，实际以管理后台配置为准（见 2.2.6）。

| 近 24 小时第 N 次 | 档位人数 |
| --- | --- |
| 第 1–4 次（已成功 0–3 次） | 0（不排队，按原流程转接） |
| 第 5–7 次 | 2 人 |
| 第 8–12 次 | 随机 4–6 人 |
| 第 13 次及以上 | 随机 10–30 人 |

| 本周累计第 N 次 | 附加人数（取最高一档，不叠加） |
| --- | --- |
| 第 1–29 次 | 0 |
| 第 30–49 次 | +5 |
| 第 50–79 次 | +12 |
| 第 80 次及以上 | +20 |

- 随机数在进入排队时一次确定，之后不再变化。
- 日档位为 0 但每周附加不为 0 时同样排队（例如近 24 小时 4 次、一周累计到第 30 次，排队 5 人）。
- 初始排队人数为 0 时完全按现有流程处理，客户无感知。
- 档位与附加人数在管理后台配置，运营可随时调整，无需改代码或重启服务。

#### 2.2.3 排队过程

1. **进入排队**：初始人数 > 0 时，不进入转人工流程（不改会话状态、不预留坐席、不打转人工标签），AI 发送排队提示：

   > 当前咨询人数较多，您前面还有 **N** 位用户在排队，预计等待约 **M** 分钟。排队期间您可以继续描述问题，我会先为您解答；轮到您后请再次发送「转人工」。

   M = N × 每人预计等待秒数（默认 40 秒，后台可配），向上取整到分钟，至少 1 分钟。

2. **动态递减**：每隔 30–50 秒（默认值，后台可配；每一步单独随机）排队人数减 1，单调递减不回升。实现上只保存“进入排队时间 + 初始人数 + 随机种子”，客户每次询问时按已过去的时间推算当前人数，不需要后台定时任务，也不需要主动推送消息。

3. **排队中**：
   - 客户再次发送转人工：不计次、不重新排队，回复当前剩余人数与预计时间；
   - 客户咨询其他问题：AI 照常应答，与平时一致；
   - 会话被解决、客户新开会话：排队跟随用户，不随会话重置。

4. **排队结束 → 获得一次兑现机会**：推算人数降到 0 后，用户获得**一次**兑现机会，**长期有效、不设过期时间**。持有兑现机会时，客户的下一次转人工请求不再触发排队，直接进入现有流程（在线空闲坐席判断 → 黑名单判断 → 分配）。

5. **兑现机会的消耗**：
   - 成功接入人工：兑现机会消耗，本次计入一次成功转人工。之后的请求按成功次数正常判定档位，达到门槛时再次排队，如此循环；
   - 兑现时坐席繁忙（或无法确认坐席状态）：回复现有“坐席繁忙”话术，**不消耗**兑现机会、不计次，客户之后再请求仍直接走转人工流程、不排队。

#### 2.2.4 与其他功能的关系

| 场景 | 处理 |
| --- | --- |
| 黑名单用户 | 排队判断在黑名单判断之前，黑名单用户同样会看到排队；排到后仍得到“坐席繁忙”话术，对客户表现一致，不暴露拉黑状态。黑名单拒接与坐席繁忙同样处理，不消耗兑现机会、不计次（黑名单用户只有拉黑前的成功转人工计入次数） |
| 转人工功能关闭 | 不计次、不排队，保持关闭时的原有行为 |
| 坐席在 Chatwoot 手动接入/分配 | 不受影响，门槛只作用于客户发起的转人工 |
| 统计报表 | 排队拦截不属于转人工，不产生转人工时间、发配量、流单；“繁忙拒接”不包含排队拦截 |
| 归档 | 排队提示作为 AI 消息正常归档，可按关键词查到 |

#### 2.2.5 数据与可靠性

- ICS 主库新增三张表，服务启动时自动创建（`CREATE TABLE IF NOT EXISTS`）：
  - 转人工次数：**每个用户一行**，不另建明细表。字段为工作区、联系人、近 24 小时成功时间列表、周次数、周次数所属周（该周的周五 09:00）、最后一次计数的消息 ID、更新时间。
    - 写入：转接成功时用一条 `INSERT … ON CONFLICT DO UPDATE` 原子更新，并发请求不会多计或少计。成功时间列表先剔除早于“当前 − 24 小时”的时间，再追加本次成功时间；周字段所属周不是本周时先置为 1，否则加 1。两部分各自独立，互不影响；
    - 读取：日计数 = 列表中晚于“当前 − 24 小时”的时间个数（读取时现算，不依赖列表是否已剔除）；周次数所属周已过期的按 0 处理。到期即不计入，不依赖定时任务准时执行；
    - 体量：列表只记成功分配到坐席的时间，且只保留 24 小时内的，每人通常只有几条到十几条；
    - 去重：本次消息 ID 与“最后一次计数的消息 ID”相同则不再加 1，用于防止 webhook 重试重复计数；
    - 清理：近 24 小时无成功记录、周次数也已过期的行没有用处，后台随排队压缩任务每 10 分钟删除。表里只剩近 24 小时或本周有过成功转人工的用户，每人一行。
  - 排队状态：**不做持久留存，只保存仍在生效的状态**，每个用户最多一行：
    - 排队中：初始人数、进入时间、随机种子，以及进入时使用的递减间隔上下限（保证后台改配置后已排队用户的推算不变）；
    - 排队归零后：立即清掉人数、种子等排队数据，只留“持有兑现机会”标记；
    - 成功接入人工：整行立即删除；
    - 不保留排队历史。后台每 10 分钟把已归零的排队行压缩为兑现标记，避免堆积无效内容。
  - 排队配置：保存后台设置的当前配置及修改记录（修改人、修改时间、修改前后内容），见 2.2.6。
- 使用独立小连接池（最多 2 个连接，语句 3 秒、锁 2 秒上限），不占用 webhook / 转人工主连接池。
- **故障放行**：计次或排队读写失败时按原流程处理并记录告警日志，不能因为门槛模块异常让客户无法转人工。

#### 2.2.6 管理后台配置

排队策略需要经常调整，参数统一在管理后台（`admin.html`）新增的“转人工排队设置”页配置，仅管理员可见、可改。

| 项 | 说明 |
| --- | --- |
| 可配置内容 | ① 总开关（开启/关闭排队）；② 日档位表：每行“近 24 小时第 X 次起 → 排队人数”，人数可填固定值或随机区间（如 4–6），可增删行；③ 周附加表：每行“本周累计第 X 次起 → 附加人数”，取最高一档不叠加，可增删行；④ 人数递减间隔上下限（秒）；⑤ 每人预计等待秒数（用于提示中的预计分钟数） |
| 默认值 | 首次启动时用 2.2.2 表格与 2.2.3 中的数值初始化；环境变量只作为初始值来源 |
| 生效方式 | 点“保存”后立即生效，无需重启服务；多实例部署时各实例不超过 30 秒同步到新配置 |
| 对已排队用户 | 改配置只影响**之后新进入排队**的用户；已在排队中的用户人数、递减节奏按进入时的配置继续推算，不跳变 |
| 校验 | 档位按起始次数从小到大排列、不得重复；随机区间下限 ≤ 上限；人数 0–200；递减间隔 5–600 秒且下限 ≤ 上限；每人预计等待 5–600 秒。不合规时不允许保存并标出错误项 |
| 修改记录 | 每次保存记录修改人、时间和修改前后内容，页面可查看最近修改记录；并发保存以版本号防冲突（提示“配置已被他人修改，请刷新”） |
| 故障兜底 | 配置读取失败时沿用最后一次读取成功的配置；服务启动即读取失败时用默认值，并记录告警 |
| 不放后台的项 | 日计数窗口（24 小时）、周清零时刻（周五 09:00）属于计数口径，不在后台调整，避免改动后历史次数含义混乱 |

### 2.3 验收用例

> 可通过调整测试数据的成功时间或测试环境时钟模拟 24 小时过期与周清零。下表前置条件中的“已有 N 次”“累计 N 次”均指**成功转人工**次数，“近 24 小时”以发起请求的时刻往前推算；“第 N 次请求”指本次若成功将是第 N 次。除 R1-23 起的配置类用例外，均按默认配置。

| 编号 | 前置条件 | 操作 | 预期结果 |
| --- | --- | --- | --- |
| R1-01 | 用户近 24 小时无成功记录，有空闲坐席 | 第 1–4 次分别发送“转人工”（每次转接成功后解决会话） | 每次都直接转接，无排队提示 |
| R1-01a | 近 24 小时成功 2 次，另有 6 次因坐席繁忙被拒 | 再发送“转人工”，有空闲坐席 | 按第 3 次判定，不排队，直接转接；被拒的 6 次不计入 |
| R1-01b | 近 24 小时用户共发起 10 次请求，其中 4 次转接成功、6 次坐席繁忙 | 查询转人工次数表 | 该用户只有 1 行，成功时间列表为 4 条，坐席繁忙不增加记录 |
| R1-02 | 近 24 小时已成功 4 次 | 第 5 次发送“转人工” | 回复排队 2 人；会话状态不变、未分配坐席、AI 仍可回答；次数不变 |

## 三、R2 所有导出/统计：数据过多则无法操作，导出可以较慢

### 3.1 当前情况

- **统计报表**：坐席细化、质检统计按时间区间现场扫描全部消息并排序计算，没有每轮预计算结果，也缺少按时间的索引。拉长到月/年时超过 8 秒时限，页面显示“统计查询暂不可用”；并且一次超时会把整个归档模块判为不可用，其他归档页面也一起报错。
- **Excel 导出**：有用户数/消息数/数据量上限，但超限只提示“当前结果过多”，看不出超了哪一项；导出在 ICS 主进程内执行，与 webhook 处理争用资源。
- **归档查询**：默认查询全部历史，进入页面即全量扫描；按月查询消息表缺少发送时间索引。
- 没有离线留档能力（见 R8）。

### 3.2 设计方案

总原则：**服务器安全优先，导出可以慢；数据超出承受范围时明确拒绝并告诉用户怎么缩小范围，不让请求拖垮服务。**

| 环节 | 方案 |
| --- | --- |
| 统计报表提速 | 处理程序整理会话时预计算每轮指标（转人工后有效访客消息数、各坐席首响时长、响应总次数、响应总时长与单轮平均响应（单轮平均仅供归档展示）、繁忙拒接/人工回复/AI 回复标记、主责坐席、咨询时长区间），写入事实表 `ops.round_service_facts`、`ops.round_seat_timings`；报表只汇总。轮次或消息变化时由触发器删除该轮结果，缺失的轮次按同一规则现场计算，回填前后结果一致。历史数据在处理程序空闲时自动回填 |
| 索引 | 轮次开始/最后消息/转人工/分配/解决/评价时间、责任坐席、收件箱、消息发送时间、坐席公开回复建立索引（迁移 011） |
| 统计超时 | 按指标拆成多条语句，各自 8 秒时限；超时提示“查询超时：所选范围内数据过多，请缩小时间范围或增加筛选条件后重试”；超时**不再**把归档模块判为不可用 |
| 归档查询 | 首次进入默认查询近 1 个月（按轮次开始时间），“重置”也恢复近 1 个月；提交时若除时间依据外没有任何条件，弹窗提醒“建议按需筛选”，取消则不查；查询超时给出缩小范围提示 |
| Excel 导出 | 保留上限（轮次/用户 2 万、消息 10 万、数据 128 MiB，可配置），超限时逐项列出“实际数量 / 上限”，并引导改用离线 HTML 留档；不生成部分文件 |
| 统计报表导出 | 与报表同口径、同上限，超限明确拒绝 |
| 离线 HTML 留档 | 生成前先预估（消息/轮次/客户/附件/页面大小）：无数据不生成；超过提醒线（3 万消息或 5000 轮，或页面预计超 500 MB）需二次确认；超过硬上限（30 万消息或 5 万轮）或预估 60 秒内算不完直接拒绝。生成在独立低优先级子进程（nice 19、平均 0.5 核、内存 4 GiB 上限、24 小时超时），同一时间只允许一个任务；子进程在同一快照内再次计数兜底 |

## 四、R3 平均响应时长测算优化

### 4.1 当前情况

图 1（需求方截图）中部分坐席的平均响应时长与实际体感**显著偏离**。分析生产口径，主要原因有：

1. **多人接待的轮次分别计入各自坐席**：交班或同事帮忙时，同一轮内每位回复过的坐席都会计入响应样本，首响归“第一个回复的人”。帮忙的同事会背上前一位坐席留下的长等待；样本少的坐席被一两轮极端值拉偏。
2. **归属不唯一**：报表按“实际回复人”归属，而质检、发配按 ICS 分配坐席，同一轮在不同报表里属于不同的人。
3. **卡片与报表两套算法**：归档客户卡片的首响从转人工时间计，报表从转人工后客户第一条有效消息计；卡片用程序逐条计算、报表用 SQL 计算，同一轮两处数值对不上。
4. **计时起点取客户连续发言的第一条**：客户习惯把一句话拆成多条分段发送，坐席为了不打断客户会等客户说完再回复。现口径从第一条未回复消息开始计时，客户打字的时间被算成坐席的响应时间，分段越多响应越“慢”。
5. 长区间现场计算慢，容易超时，见 R2。

### 4.2 设计方案

| 项 | 规则 |
| --- | --- |
| 归属 | 每轮只归**主责坐席**（ICS 已确认分配的坐席；无分配记录时为转人工后第一个有效公开回复的坐席） |
| 协助轮次 | 同一轮内只要有主责以外的坐席在转人工后有效公开回复（无论主责本人是否回复），该轮**整轮不计入任何坐席**的首响、平均响应及其他考核指标，合计也不含；只保留发配量（咨询状态总时长另见 R11）。归档卡片对此类轮次标注“协助接待”并说明原因 |
| 首响 | 按转人工发生时间选择轮次。取该轮**转人工成功后**坐席的**首次**有效公开回复，计算它与此前客户**最后一条**有效消息之间的时差。客户分段发送时以最后一段为计时点，坐席等客户说完再回复不算慢；此前客户只发过转人工指令时，以该指令为计时点 |
| 平均响应 | 首段为首响；之后从客户连续发言的**最后一条未回复消息**到下一条有效人工回复为一段；连续人工回复、未回复的尾段不计 |
| 异常值 | 单段**严格超过 600 秒**的响应剔除（从时长和样本数中同时移除，不截断为 600 秒）；600 秒与真实 0 秒保留；首响超时显示“超时不计”，不用后续回复替代首响 |
| 汇总方式 | **按次数加权，不区分轮次**：每轮在事实表中记录该坐席的**响应总次数**和**响应总时长**（只含未被剔除的段，首响计入其中），同时保存该轮**平均响应**（总时长 ÷ 总次数）供对话归档卡片、筛选和离线 HTML 显示单轮数值；**单轮平均不参与报表汇总**。统计时把所选范围内所有轮次的总时长相加、总次数相加，平均响应 = 总时长 ÷ 总次数。不先算每轮平均再求平均，避免一轮只有一两次慢回复就把整体拉高（例：一轮 3 次共 30 秒，另一轮 1 次 30 秒，结果 (30+30)÷(3+1)=15 秒）。首响每轮只有一次，按所有轮次首响的总时长 ÷ 计入的首响次数汇总 |
| 一致性 | 规则只定义一份（`service_facts.py`），统计报表、报表导出、归档卡片与筛选、Excel 导出、离线 HTML 使用同一口径；规则变化时提升规则版本号，旧结果自动现场重算并回填 |

## 五、R4 历史对话阅读区收窄、配色区分、归档界面紧凑与阅读布局

### 5.1 当前情况

- 聊天记录区随详情窗口铺满，宽屏下左右消息相隔很远；气泡固定占 88% 宽度，短消息也被拉成长条（图 2）。
- 左侧轮次目录固定 180px，字号偏小。
- 配色：真人客服气泡为浅蓝 `#eaf2ff`，AI 为浅紫 `#f1e8ff`，内部备注为浅黄，客户为浅灰。浅蓝与浅紫在色弱模拟下几乎无法区分（色差 ΔE≈3–5）。
- 离线 HTML 留档的配色与后台不一致（AI 绿、人工蓝）。
- **解释性文字过多**：对话归档模块到处是淡灰色说明（`#667085`，10–12px），如标题下的“筛选客户，点击记录在右侧阅读连续对话。所有时间均为北京时间。”、筛选区底部一大段默认范围说明、“Excel 导出包含全部匹配结果，不限当前页。”、筛选概况说明、离线留档说明、质检备注提示、消息版本说明等，占用纵向空间，界面松散。
- **页码看不清**：“第 N / M 页”等页码标记用同样的淡灰小字（12px），轮次目录页码更小；打开对话后客户列表进入紧凑模式，字号进一步缩到 10px 左右，几乎看不见第几页。
- **选中的客户不在视野里**：按客户查看时，点开某个客户后客户列表变成左侧紧凑列表，但列表不会滚动到刚才点的那一项，常常要在列表里重新翻找当前客户。
- **阅读布局**：对话详情窗口内，轮次目录在左侧整列，质检模块、“对话资料详情”、黑名单信息依次堆在聊天区上方，聊天内容被压到下半部分，一屏能看到的消息少，需要频繁滚动。

### 5.2 设计方案

#### 5.2.1 阅读区与配色

| 项 | 方案 |
| --- | --- |
| 阅读区宽度 | 聊天区最大宽度 760px 并居中；气泡按内容自适应宽度（最小 240px，最大 82% / 600px） |
| 客服气泡 | 改为浅绿色 `#cdebd6`（与 AI 浅紫在色弱模拟下 ΔE≈16–19） |
| 内部备注 | 加深黄色 `#fff2c7` 并加虚线边框，不只靠颜色区分 |
| 其他 | AI 浅紫、客户浅灰、系统消息灰色居中保持不变 |
| 离线 HTML | 与后台统一：客服浅绿、AI 浅紫、内部备注黄色虚线框、客户白/浅灰 |

#### 5.2.2 归档界面紧凑

| 项 | 方案 |
| --- | --- |
| 删除解释性文字 | 对话归档模块内淡灰色的说明性文字全部删除，包括 5.1 所列各处。保留会变化的状态与告警（如“正在检查归档状态”、查询失败、超限提示、保存成功/失败），以及查询全部历史前的确认提醒；时间字段标签中的“北京时间”字样保留 |
| 页码醒目 | 归档列表、对话消息、轮次目录、消息版本的页码统一改为深色（正文色 `--ink`）、13px、半粗；打开对话进入紧凑模式后也不缩小 |

#### 5.2.3 选中客户置顶可见

- 按客户查看时，点开某个客户后，左侧客户列表自动滚动，让该客户卡片停在列表可视区**第一位**并保持高亮，不需要再翻找。
- 只滚动、不改变列表顺序和分页；切换上一个/下一个客户时同样滚动到位。
- 按轮次查看时同理，当前轮次停在列表可视区顶部。

#### 5.2.4 对话详情布局

原则：**对话紧凑地放在屏幕正中，尽量多显示消息、减少滚动；右上角放质检，右下角放轮次目录。**

| 区域 | 方案 |
| --- | --- |
| 中间：对话 | 聊天区占据中间整列、从窗口顶部铺到底部，宽度按 5.2.1（最大 760px 居中）；消息分页按钮放在聊天区下方一行。标题栏压缩为一行（客户名 + 导出本轮 / 客户完整历史 / 关闭） |
| 右上：质检 | 现在的“本轮质检”模块（轮次选择、AI/人工质检、备注、保存）整体移到右侧栏上部；“对话资料详情”和黑名单信息作为折叠项放在质检下方，默认收起 |
| 右下：轮次目录 | “全部聊天记录”与轮次列表移到右侧栏下部，占满剩余高度、独立滚动，目录分页在其底部 |
| 右侧栏宽度 | `clamp(260px, 26%, 340px)`；质检区最高占右侧栏 45%，超出时内部滚动，保证轮次目录始终可见 |
| 窄屏 | 1250px 以下右侧栏收窄到 240px；900px 以下右侧栏改为聊天区上方的“质检 / 轮次”两个折叠按钮，聊天区占满宽度 |
| 离线 HTML | 离线页面的聊天区同样居中；其轮次目录与页内筛选不在本次调整范围 |

## 六、R5 筛选优化：只输出命中结果，点进去就是命中的那段对话

### 6.1 当前情况

- “按客户”视图中，筛选条件只用于**选出客户**；点开客户后显示该客户的**全部历史**。例如筛选坐席 A，点开客户能看到其他坐席接待的轮次，质检时容易标错轮次。
- 客户卡片上的轮次数、最近一轮按客户全部历史计算，与筛选无关。
- 按客户导出筛选结果时，导出的是这些客户的完整历史（例如用“已评价”筛选，导出了 148 条全历史）。
- 每轮显示为“第 N 轮”，但编号只在单个 Chatwoot 会话内递增；用户每次咨询多为新会话，按客户看几乎全是“第 1 轮”。

### 6.2 设计方案

| 项 | 方案 |
| --- | --- |
| 轮次级筛选的判定 | 除来源、账号、用户搜索、黑名单外，任一条件（时间、坐席、评价、质检、关键词、接待分类、流单等）都视为轮次级筛选 |
| 按客户列表 | 只列出有命中轮次的客户；卡片上的轮次数、最近一轮按**命中轮次**统计，另显示“共 N 轮”供参考 |
| 客户详情 | 目录只列命中的轮次，标题显示“命中 N 轮”；默认打开第一条命中轮次；“客户完整历史”按钮在轮次级筛选下隐藏 |
| 按轮次视图 | 点击哪一轮就打开哪一轮；如需看全貌，可点“用户全史” |
| 纯消息类条件 | 关键词等条件命中未归轮消息时，详情只显示命中的那几条 |
| 导出 | Excel、离线 HTML 在轮次级筛选下一律只导出命中轮次（每轮完整消息），与列表、详情一致；导出确认框列出当前已应用的筛选 |
| 轮次名称 | 改为“用户第 N 次咨询 · 会话 X · 会话内第 N 轮”。“用户第 N 次咨询”按该用户全部轮次的开始时间查询时现算，不改表结构 |

### 6.3 验收用例

| 编号 | 操作 | 预期结果 |
| --- | --- | --- |
| R5-01 | 按客户视图筛选坐席 A，点开某客户 | 目录只有 A 负责的轮次，显示“命中 N 轮”；看不到其他坐席的轮次 |
| R5-02 | 筛选“评价分数=1 分”，按客户打开 | 只显示 1 分的那一轮，默认定位到该轮 |
| R5-03 | R5-01 状态下导出 Excel | 只含命中轮次，不含该客户其他轮次 |
| R5-04 | R5-01 状态下生成离线 HTML | 与 Excel 范围一致 |
| R5-05 | 只按“用户搜索”筛选 | 显示该用户完整历史（非轮次级筛选） |
| R5-06 | 按轮次视图点击某轮 | 打开的就是这一轮 |
| R5-07 | 某用户分 3 次在 3 个会话咨询 | 依次显示“用户第 1/2/3 次咨询”，各自“会话内第 1 轮” |

## 七、R6 黑名单功能优化：可备注、归档、可查

### 7.1 当前情况

- 拉黑只有坐席在 Chatwoot 网页端使用的“静音”入口（联系人 blocked），由 ICS 统一按 24 小时到期自动解除。
- 不能选择时长，不记录拉黑原因、操作人、解除原因；同一联系人再次拉黑会覆盖上一次记录，没有历史。
- 归档中查不到哪些用户被拉黑过，也看不到拉黑记录。
- 拉黑的客户转人工时，会话被直接置为“已解决”，触发满意度评价，客户能察觉被拉黑。

### 7.2 设计方案

| 项 | 方案 |
| --- | --- |
| 拉黑入口 | **唯一入口**为坐席客户端工具栏“拉黑”按钮（不注入 Chatwoot 页面），弹窗核对客户信息 |
| 网页端静音与黑名单脱钩 | （2026-11-11 调整）保留 Chatwoot 网页端原有的静音 / 取消静音按钮，但它只保留 Chatwoot 自身的功能，不再影响黑名单：ICS 不再处理静音回调，静音不会加入黑名单，取消静音也不会解除拉黑；黑名单拉黑、修改、解除、到期也不再改动 Chatwoot 静音 |
| 时长 | 2 小时 / 24 小时 / 72 小时 / 永久，共四档（不支持自定义）；2 小时为短时拉黑，用于临时刷屏、情绪激动等需要短暂冷却的场景；弹窗默认仍为 24 小时；修改时长从修改时刻重新计算，四档之间可任意互改 |
| 原因（必填） | 取消预设原因选项，统一为一个“原因（必填）”文本框，由坐席人工打字填写；去除首尾空格后不能为空，最多 500 字。客户端与 ICS 服务端同时校验，接口提交空原因返回 422。已有历史记录中的预设原因照常显示 |
| 黑名单管理 | 客户端“黑名单”窗口列出所有拉黑中的客户；任何坐席都可修改时长或解除；**修改时长必须填写修改原因、解除必须填写备注**（均为人工填写、必填）；并发修改以版本号防冲突（提示“已被他人修改”） |
| 记录与归档 | 每次拉黑、修改、解除、到期都记录操作人、时间、原因/备注，写入 ICS 历史表并同步到归档库（迁移 012） |
| 旧记录兼容 | 升级前由网页端静音产生的黑名单记录照常显示（标注“Chatwoot 网页端、未填写原因”），到期或手动解除后失效；升级前的记录到期或解除时顺带取消一次 Chatwoot 静音 |
| 查询 | 对话归档新增“黑名单”筛选：曾被拉黑 / 当前拉黑中；客户详情展示完整拉黑记录（时间、操作人、时长、原因、解除备注），列表带拉黑标签 |
| 对客户的表现 | 拉黑后 AI 继续正常接待，只拒绝转人工；拒绝话术与“坐席繁忙”完全相同，不触发满意度评价，客户无感知。拉黑时若正在人工接待，按正常结束处理 |
| 主链路影响 | 转人工拒接只看 ICS 黑名单（未到期的拉黑记录），不再看 Chatwoot 联系人 blocked 状态；黑名单查询失败时按原规则暂不转人工。黑名单接口使用独立小连接池，故障只影响黑名单接口 |

## 八、R7 快捷语绑定客服坐席账户

### 8.1 当前情况

- 坐席客户端的“我的快捷回复”只保存在本机。换电脑后需重新录入；同一台电脑切换坐席账号时，看到的是上一个人的快捷回复。

### 8.2 设计方案

| 项 | 方案 |
| --- | --- |
| 绑定关系 | 快捷回复按“Chatwoot 工作区 + 坐席账号”保存在 ICS 数据库（`agent_quick_replies`，启动自动建表），每个坐席一份 |
| 身份核对 | 客户端转发当前 Chatwoot 登录凭据，ICS 向 Chatwoot 核对操作人；坐席只能读写自己的那一份，不信任客户端传入的用户 ID |
| 多设备 | 任何电脑登录都取回同一份；同一电脑切换坐席自动切换内容，其他坐席看不到 |
| 离线缓存 | 本机保留缓存：ICS 暂时连不上时 F1 仍可用缓存，管理窗口只读、不能修改，恢复连接后即可修改；客户端未登录强提醒服务或服务器未启用本功能时，修改暂存本机，连上后自动上传 |
| 旧数据迁移 | 旧版只存本机的快捷回复，在该坐席首次连上服务器时自动上传；服务器已有内容时，把本机独有的回复（按标题 + 内容去重）追加到末尾 |
| 冲突 | 以版本号乐观锁，另一设备已修改时提示刷新，不静默覆盖 |
| 使用方式 | 不变：输入框按 F1 弹出，每页 5 条，1–5 填入，Q/E 翻页 |
| 限制 | 每人最多 200 条；标题 1–80 字，内容 1–12000 字，合计不超过 30 万字 |

### 8.3 验收用例

| 编号 | 操作 | 预期结果 |
| --- | --- | --- |

## 十、R9 质检结论按钮优化（不默认合格）

### 10.1 当前情况

- 每轮质检有“AI 质检”“人工质检”两个下拉框，初始均为“待定”，需要逐个手动选择后再点保存。
- 不区分接待场景：纯 AI 接待的轮次也可以填写“人工质检”结论，容易误填并影响人工不合格统计。
- 控件为 11px 小字下拉框，质检人员每天大量操作，点选费时且容易误点。

### 10.2 设计方案

#### 10.2.1 原则

- **不默认合格**：打开未质检过的轮次时不预选任何结论，按钮均为未选中状态；质检人员必须主动点击结论按钮。未点击的轮次在统计中为“待定”，不因打开查看而变化。
- **一键保存**：结论按钮即保存按钮，点击后立即保存“AI 结论 + 人工结论 + 当前备注”，不需要再点“保存”。
- 按轮次接待分类显示不同的按钮组，结论组合固定，避免逐项选择。

#### 10.2.2 按钮与保存结果

| 场景 | 按钮 | 保存结果（AI 质检 / 人工质检） |
| --- | --- | --- |
| 纯 AI 接待 | 【AI合格】 | 合格 / 空（不适用） |
| | 【AI不合格】 | 不合格 / 空（不适用） |
| 人工介入（必有 AI 在前） | 【全部合格】（高频，加大） | 合格 / 合格 |
| | 【人工合格】 | 不合格 / 合格 |
| | 【AI合格】 | 合格 / 不合格 |
| | 【均不合格】 | 不合格 / 不合格 |

- 人工介入的四个按钮对应 AI、人工两项结论的全部四种组合：“人工合格”指仅人工合格（AI 不合格），“AI合格”指仅 AI 合格（人工不合格）。按钮上以小字注明另一项结论（如“人工合格”下方注“AI 不合格”），避免误解。
- 纯 AI 轮次不显示人工质检，人工结论保存为空，统计中不计入人工质检。服务端同样校验：纯 AI 轮次提交人工结论时拒绝（422），防止绕过页面写入。
- 轮次接待分类以保存时为准；纯 AI 轮次后来转人工变为人工介入时，按钮组自动切换为人工介入的四个按钮，原 AI 结论保留展示，需重新点选完整组合。

#### 10.2.3 已保存与修改

| 项 | 规则 |
| --- | --- |
| 已保存的轮次 | 高亮与已保存结论对应的按钮，并显示保存时间与操作人 |
| 修改结论 | 直接点击另一个按钮即覆盖保存，保留历史版本 |
| 修改备注 | 改完备注后点击当前高亮按钮（或 Ctrl+Enter）重新保存；备注未保存时按钮旁提示“备注未保存” |
| 历史数据 | 旧版本保存的“待定”或单项结论原样显示；人工介入轮次中只填了一项的，对应组合不高亮，提示“结论不完整”，点任一按钮补全 |
| 并发 | 以版本号防覆盖，后保存者提示“已被他人修改，请刷新”（保持现状） |
| 备注 | 选填，最多 5000 字，默认 3 行可拉伸；建议先写备注再点结论按钮 |

#### 10.2.4 高频操作 UI

| 项 | 方案 |
| --- | --- |
| 布局 | 按钮横向一行排列；人工介入时【全部合格】宽度约为其他按钮的 2 倍、高度 ≥40px、字号 15px 加粗、绿色主按钮，放在最左；其余三个按钮高度 ≥34px、字号 13–14px。质检区位于详情右侧栏（见 R4，宽 260–340px），宽度放不下一行时【全部合格】独占第一行通栏，其余三个在第二行等宽并列 |
| 配色 | 合格类按钮为绿色系，【AI不合格】【均不合格】为红色系，【人工合格】【AI合格】（各含一项不合格）为橙色系；选中态实心填充，未选中为描边 |
| 防误点 | 按钮之间间距 ≥8px；保存中按钮置灰，防止连点重复提交 |
| 场景标识 | 按钮上方显示当前轮次接待分类（纯 AI / 人工介入） |

## 十一、R10 时间筛选：日期为一级、具体时刻为二级菜单

### 11.1 当前情况

- 对话归档的开始/结束时间使用浏览器原生“日期时间”控件，日期和时分在同一个弹窗里，弹窗没有“确定”按钮，必须点空白处才能关闭。
- 结束时间为“不含该时刻”，要查完整的一天需要把结束时间设为第二天 00:00，容易少查一天。
- 各处时间选择方式不统一：
  - 统计报表只能按整日选择；
  - 坐席状态“全天分钟核对”使用原生时间控件；
  - 离线 HTML 页面内用“日期时间”控件，结束时间“不含”。
- 控件偏小，高频操作不便。

### 11.2 设计方案

**统一策略**（所有涉及时间选择的地方均采用）：

| 项 | 方案 |
| --- | --- |
| 一级：日期 | 开始日期、结束日期使用日期选择（点选日期即关闭） |
| 二级：具体时刻 | 日期下方“指定时刻”展开项，展开后出现“时”“分”下拉；不展开即不指定 |
| 默认时刻 | 未指定时：开始时间 = 开始日期 00:00:00；结束时间 = 结束日期 23:59:59（**包含**） |
| 只选“时”不选“分” | 开始取 HH:00:00，结束取 HH:59:59 |
| 内部取值 | 页面显示为闭区间，提交时转换为半开区间（结束 23:59:59 → 次日 00:00 不含），后端口径不变 |

| 快捷范围 | 提供“今天 / 昨天 / 近 7 天 / 近 30 天 / 本月 / 上月”按钮 |
| 校验 | 结束早于开始时提示并阻止查询 |
| 尺寸 | 日期框、下拉、快捷按钮高度 ≥34px |

**适用范围**：

## 十二、R11 咨询状态总时长改为本次服务的人工时长

### 12.1 当前情况

- 生产口径：每轮取坐席**第一次公开回复到最后一次公开回复**的整段，再合并该坐席所有轮次。
- 问题：
  1. 起点不是转人工，而是坐席第一条回复，等待时间不计；
  2. 会话长时间不点“解决”、客户隔几小时再来问时，中间空档整段计入，合并后生产出现**单日 19 小时**的咨询时长；
  3. 多位坐席回复同一轮时各算一段，同一轮重复计入。
- 归档卡片“本轮总时长”从轮次开始算到解决，包含 AI 阶段，与报表口径不同。

### 12.2 设计方案

咨询状态总时长 = 本轮**从转人工成功到本次对话“解决”**的时长，中间的长空档不计：

| 项 | 规则 |
| --- | --- |
| 起点 | 该轮转人工成功时刻 |
| 终点 | 该轮被“解决”的时刻 |
| 空档切分 | 在起点到终点之间，把转人工成功、每条有效消息（客户公开消息或坐席公开回复，不论谁发）、解决依次排成时间线。相邻两点间隔**超过 600 秒**（恰好 600 秒仍连续）即判为 2 次咨询，空档不计 |
| 每次的起止 | 每次咨询从空档后的第一条消息（第一次为转人工成功时刻）开始；以空档前的最后一条消息为终点；最后一次咨询以“解决”为终点（解决距上一条消息超过 600 秒时，以上一条消息为终点） |
| 总时长 | 该轮各次咨询时长之和 |
| 未解决的轮次 | 暂以最后一条有效消息为终点；解决后按上述规则重算；不延长到查询时刻 |
| 归属 | 主责坐席。协助轮次也计入主责坐席（这是协助轮次中唯一保留的考核项） |
| 汇总 | 合并该坐席各次咨询的重叠、嵌套、相邻时段，只累计落在筛选区间内的部分；跨日/跨月正确切分 |
| 计算方式 | 各次咨询区间在处理程序整理会话时预计算存入事实表（迁移 014），报表只汇总；未回填的轮次按同一规则现场计算。归档卡片、离线 HTML 显示同一数值 |

| --- | --- | --- |
| R11-01 | 10:00 转人工成功，10:01–10:20 往来（间隔均 <10 分钟），10:25 点解决 | 1 次，计 25 分钟（10:00–10:25） |
| R11-02 | 10:00 转人工成功，往来到 10:10；客户 14:00 再发问，坐席 14:05 回复，14:08 点解决 | 判为 2 次：10:00–10:10（10 分钟）+ 14:00–14:08（8 分钟）= 18 分钟 |

## 十四、R13 统计报表新增用户成功转人工排行（前 100 名）

### 14.1 当前情况

- 统计报表只有按时段汇总（时间统计）和按坐席归属（坐席细化，含“发配量”）的转人工数据，看不到是**哪些用户**在频繁成功转人工。
- 时间统计的“转人工量”按轮次计，包含坐席繁忙/黑名单拒接、仍在请求中的轮次，不等于成功转人工次数。
- 运营要找高频成功转人工的用户（用于评估 R1 排队档位、识别刷转人工用户、决定是否拉黑），只能在对话归档里逐个客户翻看，无法按次数排序，也无法逐条核对每次转人工的时间。

### 14.2 设计方案

| 项 | 方案 |
| --- | --- |
| 入口 | 统计报表新增“用户统计”页（`/admin#statistics/users`），与时间统计、坐席细化、质检统计并列，沿用左侧筛选与概况、右侧明细表的布局 |
| 统计对象 | 用户（account_id + contact_id，见名词说明）。同一用户在多个会话中的成功转人工合并计算；无法识别联系人的不参与排行 |
| 统计口径 | **成功转人工次数**：与名词说明中的“成功转人工”、R1 计次、坐席细化“发配量”同一口径，即 ICS 预留并分配坐席成功、会话转入人工接待记 1 次。每轮最多一次成功分配，因此同一轮内多次发送“转人工”只计 1 次 |
| 不计入 | 纯 AI 接待；坐席繁忙拒接、黑名单拒接；R1 排队拦截；仍在请求中、未分配到坐席的；坐席在 Chatwoot 网页端手动分配或沿用上一轮人工接待（无 ICS 分配记录）的；缺少分配时间的历史补录记录 |
| 时间筛选 | 按 **ICS 成功分配时间**（即转人工成功的时刻）归入区间，与发配量一致；时间选择按 R10 统一组件：按日 / 按月 / 按年 / 自定义，可展开二级时刻；默认今天全天，“重置”恢复今天 |
| 其他筛选 | 渠道（与其他报表页同一渠道筛选，默认全部） |
| 排序与名额 | 按成功转人工次数从高到低取**前 100 名**；次数相同时依次按最近一次成功转人工时间（晚者在前）、联系人 ID 排序，保证每次结果顺序稳定；不足 100 名按实际显示；次数为 0 的用户不进入排行 |
| 明细列 | 名次、用户（联系人名称 / 联系人 ID / 渠道）、**成功转人工次数**、涉及会话数、区间内首次 / 最近一次成功转人工时间、当前是否在黑名单（R6，带标签） |
| 溯源明细 | 点开某个用户，展开该用户区间内**每一次成功转人工**的明细：成功分配时间（到秒）、会话与轮次、分配坐席；每条可跳转到对话归档对应轮次。明细条数与该用户的成功转人工次数一致 |
| 分页 | 排行每页 20 名，共最多 5 页，沿用 R12 分页栏与跳页 |
| 概况 | 左侧显示：区间内成功转人工总次数（与坐席细化发配量合计一致）、有成功转人工的用户总数、前 100 名次数合计及占总次数的比例 |
| 跳转归档 | 点击用户的成功转人工次数，打开对话归档：按客户视图定位该用户，时间依据“ICS 成功分配时间”、时间范围与报表相同，只显示命中轮次（R5），轮次数与报表数字一致 |
| 字段说明 | 表头与概况带“？”提示，说明上述口径 |
| 导出 | 支持导出 Excel：数据表为当前筛选下的统计概况与前 100 名排行，另附口径说明；**不导出逐条成功转人工明细**（筛选范围大时数据量过大，明细在页面“溯源”或对话归档中查看）；文件注明起止时间到秒与渠道筛选；与报表同口径，沿用 R2 上限 |
| 数据来源 | 只读对话归档库中已有的 ICS 成功分配记录（ICS 分配成功后写入分配记录，经分配同步写入归档，写入后不覆盖、不删除），**不读取 R1 的转人工次数表、排队状态表**，与 R1 互不依赖、可分别上线；不新建表、不需要数据迁移 |
| 历史范围 | 分配同步（`ARCHIVE_ASSIGNMENT_SYNC_ENABLED`）开启之前的分配没有准确时间，不计入；页面在区间早于最早一条分配记录时提示“该时间之前无成功转人工记录” |
| 性能 | 使用已有的分配时间索引（迁移 011）按区间取数、按用户分组后取前 100，单条语句 8 秒时限；超时提示“查询超时：所选范围内数据过多，请缩小时间范围后重试”，不影响其他报表页与归档 |
| 权限 | 与统计报表其他页相同；页面不显示聊天正文 |

## 十六、风险

| 编号 | 风险 | 影响 | 应对 |
| --- | --- | --- | --- |
| K1 | 011 迁移建索引期间相关表只读 | 采集器写入超时，该时段归档事件可能丢失（智能客服与 Chatwoot 聊天记录不受影响） | 低峰执行；先用备份恢复环境演练计时；迁移后核对事件积压 |

| K4 | 口径调整（首响/平均响应/咨询时长/主责与协助轮次） | 新旧报表数值不可直接对比，坐席对考核结果可能有疑问 | 上线时公告新口径并注明生效日期；报表“？”提示同步更新；需要对比时用新口径重算历史区间 |
| K5 | 转人工排队可能误伤正常但咨询频繁的用户 | 用户等待变长，可能引起投诉 | 档位参数在管理后台随时调整、即时生效，可通过开关整体关闭；排队期间 AI 照常应答；兑现机会不过期、坐席繁忙不消耗 |
| K6 | 转人工排队模块故障 | 若处理不当会阻断转人工 | 故障放行：读写失败按原流程转接并告警；使用独立小连接池，不占主链路连接 |
| K7 | 持有兑现机会但长期不再咨询的用户 | 排队状态表每人残留一行标记 | 每人最多一行且只含标记，归零后立即清空排队数据，成功转人工即删除；数据量上限为曾排队的用户数 |
| K9 | 坐席客户端需重新分发 | 未升级的客户端无法使用黑名单、快捷回复同步 | 发布时统一推送新版本，旧版快捷回复首次连上服务器自动上传 |
| K10 | 离线 HTML 留档体积大 | 生成耗时长、占用磁盘，浏览器打开较慢 | 生成前预估与上限；子进程限速；下载后 2 小时、未下载 24 小时自动删除；磁盘预算 50 GiB |
