# 双塔 Top10 与 reranker 精排排序对比测试报告

测试日期：2026-10-10

## 测试背景

当前服务器未配备 GPU，本地 reranker 模型 `bge-reranker-v2-m3` 只能使用 CPU 推理。在现有 4 核服务器上，reranker CPU 推理和并发排队已经成为 RAG 链路的主要性能瓶颈，容易把多个同时到达的问题推迟到 30 秒超时窗口之外。

本次测试综合考虑服务器升级成本和链路优化策略，评估是否可以去除本地 reranker，直接使用双塔模型召回的 Top5 文档交给大模型生成回复。测试重点是确认双塔前排文档与 reranker 高排序文档的覆盖情况，并评估去除精排后对回复质量和成本的影响。

## 1. 测试目的与方法

本次测试逐题执行同一套排序对比逻辑：

1. 使用 BGE-M3 双塔模型从 ChromaDB 召回 Top10。
2. 使用本地 bge-reranker-v2-m3 对同一批 10 条文档全部精排。
3. 比较双塔排序和 reranker 排序的名次变化。
4. 观察直接取双塔 Top5 时，与 reranker Top5 的文档集合是否一致。

本测试只比较文档排序，不调用 LLM，也不直接评价最终回答质量。
脚本会临时把本次 reranker 输入和输出数量设为实际召回数量，不修改 .env 或线上配置。

测试脚本路径：ics_agent/rag/reranker/compare_dense_and_rerank.py

## 6. 结果解读与建议

1. 双塔 Top2 与 reranker Top2 的高匹配文档覆盖率为 85%，结合当前知识库的测试结果，直接删除 reranker、采用双塔召回 Top5 生成回复的可行性较高。
2. 可以先在测试或灰度环境尝试直接使用双塔 Top5，具体回复是否满足业务要求由业务方用真实问题进行验证，并保留快速恢复 reranker 的开关。
3. Top1 在部分问题中仍会变化，因此业务测试应重点检查充值、提现、收益、限流和交友等问题的最终回答是否引用了正确依据。
4. 去除 reranker 后，每次请求可以省去本次实测中位数约 9 秒的本地精排计算，并减少 CPU 争用、精排信号量等待和请求排队。在同一台服务器上运行 Chatwoot、数据库和 RAG 服务时，这会直接释放 CPU 余量，有助于降低并发场景下的超时概率。
5. 去除 reranker 还可以减少本地模型加载和维护成本，不需要为精排单独升级 GPU 或长期租用更高规格服务器；链路也从“双塔召回—CPU 精排—LLM”简化为“双塔召回—LLM”，故障点和调参项更少。
6. 当前切分策略为每个 chunk 小于 512 tokens。从 Top3 增加到 Top5，单次 RAG 最多增加约 2 个 chunk，输入 token 约增加 1000。按 DeepSeek 输入 token 参考价 0.04 元/百万 tokens 计算，单次增加约 0.00004 元；每 1 万次约增加 0.4 元，每 10 万次约增加 4 元，输入成本增加很低。
7. 本报告的耗时包含本机当前模型和向量库状态；不能单独证明并发能力或 30 秒端到端 SLA。
