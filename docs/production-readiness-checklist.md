# ICS + Chatwoot 生产上线验收清单

编制日期：2026-10-09。适用范围：当前 `test` 分支的 FAQ、RAG、Chatwoot AgentBot、人工接管、会话记忆和管理后台。

逐步操作、验证命令和结果判读见 [上线测试操作手册](production-test-playbook.md)。

这是待执行的验收计划，不是测试通过报告。本轮只整理清单，没有执行压测、故障注入、恢复演练或生产变更。此前的健康检查、签名探测以及用户确认的 MVP 问答成功，只能证明相应检查点已打通。

## 1. 上线门槛与测试准备

- **P0：上线阻断项。** 首答丢失、重复回复、串会话、越权、错误转人工、错误资金规则等问题未关闭，不进入全面生产。
- **P1：上线前必须验收的质量与运维项。** 未达到目标时，必须有明确的限流、降级或人工承接方案，并由业务和运维确认是否只开放小流量。
- 每项状态填写：未测 / 通过 / 失败 / 阻塞。不能把“没发现异常”或“HTTP 返回 200/202”直接记为通过。
- 故障注入、清理测试、并发压测和恢复演练使用隔离环境、测试 Inbox、虚拟用户及测试数据；环境版本、资源和配置应与拟上线版本一致。
- 先确定预计峰值：同时咨询人数、每秒进入的消息数、每会话发言频率、FAQ/RAG 比例、在线人工坐席数和日调用成本预算。用户人数不等于正在执行的 RAG 请求数。
- 每次保留：代码提交、镜像版本或摘要、配置版本（脱敏）、知识库版本、模型版本、执行时间、测试人、消息 ID、会话 ID、任务 ID、实际结果和截图或日志。
- 当前已核对的服务器查询预算曾为 30 秒；代码省略该变量时的默认值不同。以验收时运行容器配置为准。该预算不包含完整队列等待和回复送达时间。

## 2. 当前版本需要优先验证的可靠性缺口

### 2.1 接收成功后崩溃可能丢失待办

当前待处理消息保存在进程内队列。事件表记录摘要和状态，没有完整的自动恢复与重放链路；启动时不会重放数据库里的所有未完成事件。已有 `queued` 记录还会被重复事件检查直接拒绝。因此，“Webhook 已返回 202 → 排队期间进程崩溃 → 再次投递”不能假定会自动恢复。

对应测试 E04。若生产要求已接收消息不丢失，需要在上线前完成持久化任务和恢复机制。仅有监控和人工补偿时，应明确限定为有人工值守的小流量试运行，不能宣称满足可靠投递要求。

### 2.2 发送结果不确定时可能重复回复

当前向 Chatwoot 创建回复时未提交发送幂等键。若 Chatwoot 已经写入消息，但响应丢失，或 ICS 在记录完成状态前失败，任务重试可能再次发送。

对应测试 E05。需要验证并完善发送结果核对、去重和补偿策略；普通的入站重复事件去重不能覆盖这一故障窗口。

### 2.3 单实例与健康检查边界

当前依赖进程内队列、会话锁和 FAQ 索引。容量测试保持单应用实例，不直接通过增加多个 Uvicorn workers 或多个 ICS 副本扩容。`/health` 只说明 HTTP 可响应，不能代替模型、数据库、向量库和回复发送的就绪检查。

## 5. Webhook、并发与消息可靠性

| 编号 | 级别 | 怎么测 | 通过标准 | 证据 |
|---|---|---|---|---|
| E01 | P0 | 正确签名、错误签名、缺少签名、过期时间戳、修改签名后的请求体 | 合法请求被接收；无效请求返回 401；拒绝的请求不生成回答、任务或人工动作 | HTTP 状态、任务记录与消息数量 |
| E02 | P0 | 相同消息事件顺序重投和并发重投；已完成后再重投；同一会话多次已解决 | 同一业务消息只产生一次预期动作；新的状态变化不被旧事件误去重 | event key、任务和回复数量 |
| E03 | P0 | 同一用户快速连续发送 3～5 条；多个用户交错发送；故意延迟某个会话 | 同会话按设计处理且不串上下文；一个慢会话不阻塞所有其他用户；每条最终状态可解释 | 消息顺序、队列等待、每会话耗时 |
| E04 | P0 | 已返回 202 后，在排队中和处理中分别强制终止 ICS；恢复后重投相同事件 | 已接收请求能可靠恢复或进入可追踪补偿流程，无长期无人处理的待办；当前版本存在已知缺口，不能默认通过 | 故障前后 queued/processing 记录、补偿与最终回复 |
| E05 | P0 | Chatwoot 写入回复后阻断响应；在 ICS 记录完成前中断服务；再触发重试 | 能识别已经送达的回复，避免重复公开回答；人工动作同样无重复副作用 | Chatwoot 消息 ID、发送次数、任务状态 |
| E06 | P0 | 达到队列上限后继续发送；过载后停止施压；观察重新恢复 | 未接收消息有明确失败/重试行为；已接收消息不静默丢弃；队列能排空；无无限重试 | 入站数、受理数、拒绝数、最终完成数 |

不要把 202 当成已送达。对正常、未转人工、未被结束轮次抑制的测试消息，应逐条对账：发送 → 受理 → 处理 → Chatwoot 写入 → 用户端显示。

| O04 | P0 | 演练紧急停止机器人、切换人工或恢复原绑定，再恢复机器人 | 切换动作有明确负责人；在途消息被跟踪；用户有承接；恢复不会抢人工会话或重复处理旧消息 | 切换步骤、消息对账、耗时 |

## 10. 建议的首轮测试规模与指标

这些是待业务和运维确认的验收起点，不是已测性能，也不是所有场景通用的保证。

### 10.1 答案评测集

建议先准备 250 个有标注的测试条目，保留约 20% 作为不参与调优的验收集：

| 类型 | 建议数量 | 标注内容 |
|---|---:|---|
| FAQ 原句、改写和易混淆问题 | 100 | 正确 FAQ 或应转 RAG；预期答案要点 |
| 有知识依据的 RAG 问题 | 80 | 来源文档与段落、正确要点、禁止出现的错误事实 |
| 未知、模糊、冲突和过期资料 | 30 | 应澄清、说明不确定或转人工的行为 |
| 提示注入、越权和敏感信息请求 | 20 | 禁止泄露/执行的内容与预期拒绝行为 |
| 多轮与用户切换场景 | 20 | 整段对话、轮次边界、允许与禁止引用的记忆 |

由业务人员审核答案；不能只用模型自评。不要把维护回复、空回答或仅有检索结果计为正确回答。

### 10.2 建议放行标准

- P0 场景全部通过；关键资金、权限、隐私政策题必须正确，零跨用户数据泄露。
- 普通知识题人工判定正确率建议至少 95%；知识不足场景正确澄清/拒答/转人工率建议至少 95%。小样本通过不代表线上所有问题都正确。
- 正常、可回答的端到端测试消息成功送达正确答案比例建议至少 99%；故障提示单独统计，不充当正确答案。分别报告错误回答、未回复与重复回复。
- 在目标峰值下，建议起始体验目标：FAQ 的 P95 不超过 3 秒，RAG 的 P95 不超过 20 秒；P95 表示 95% 的消息在该时间内完成。若实际容量达不到，应先限制开放流量或优化，再由业务决定可接受目标，不能修改测试报告掩盖超时。
- 无法承诺“零丢消息”时，必须显式披露当前队列缺口，并限定灰度范围、值班、告警和补偿；不要将其记成 P0 通过。
- 恢复时间目标和最多允许丢失多少历史数据，由业务填写；备份频率、备份存放位置和恢复演练结果必须支持这两个目标。

## 11. 执行顺序与记录模板

1. 冻结拟上线版本与数据，运行仓库现有自动化回归。`tests/` 已包含会话、人工接管、并发、兜底及消息格式等测试，但其中的模拟依赖不能替代真实联调。
2. 完成 A/B/K 的业务功能、答案评测与知识更新测试，同时验证 E01/S 的基本安全边界。
3. 优先执行 E04/E05 的崩溃与发送确认故障测试，再补齐其他故障、重试和并发场景；发现架构缺口后修复并回归。
4. 在真实依赖和隔离 Inbox 上执行目标峰值压测与 24～48 小时稳定性测试。
5. 完成备份恢复、版本回退、告警和值班演练。
6. 先限定一个可控的业务范围或 Inbox，由人工值守观察；核对正确率、延迟、失败率与成本后逐步放量。每次放量保留快速回退方式。

测试环境安装依赖并使用测试配置后，可运行现有 Python 回归：

```bash
python -m unittest discover -s tests -v
```

需要在包含 `tests/` 的源码环境执行；当前后端生产镜像不保证包含测试目录。不要把单元测试通过等同于本清单全部通过。

每次执行复制以下记录：

| 字段 | 填写内容 |
|---|---|
| 用例编号 / 状态 | 例如 E04 / 失败 |
| 测试环境与版本 | 提交、镜像、配置、模型、知识库版本 |
| 前提与操作 | 用户/坐席状态、消息、并发和故障时点 |
| 预期 / 实际结果 | 对照本清单记录差异 |
| 关联证据 | 会话 ID、消息 ID、任务 ID、截图、脱敏日志或监控 |
| 缺陷与负责人 | 问题链接、严重程度、修复负责人 |
| 复测结果 | 修复版本、复测日期、通过证据 |
