归档最近 50 轮：代码检查与测试记录（2026-11-03）
================================================

结论：当前工作区代码能够解析跨多轮累计超过 20000 个事件、超过 64 MiB 的单个 Chatwoot 会话，并继续处理新增轮次。最近 50 轮以外的历史保留。首次整理和历史修复仍可能分批覆盖完整历史；单轮本身超过事件或字节预算仍会失败。

测试使用独立 PostgreSQL 16.15 临时数据库，应用 001–010 全部迁移并通过事务及权限验证。实际归档进程挂载当前工作区的 `quality/` 代码，使用 `ics-agent:py310` 镜像，资源限制为 512 MiB 内存、0.5 CPU。解析配置为最近 50 轮、索引每页 500 个事件/8 MiB、解析每批最多 20000 个事件/64 MiB。

**代码检查中保留的性能问题（P2）**

第一次大数据集成测试中，`quality/processing/replay.py` 的 `start_cursor()` 定位受影响轮次查询触发过一次 30 秒 `statement_timeout`，任务记录为 `QueryCanceled`。随后自动重试完成，最终测试通过。PostgreSQL 日志中的超时 SQL 对应读取 `facts` 并计算 `dirty` 起点的查询。

该查询仍会从当前会话截至高水位的定位索引读取历史元数据，再计算修复起点；最近 50 轮限制主要约束实际载荷解析，不能保证定位查询的耗时与历史规模无关。后续查询计划检查和实际进程验收未稳定复现同一超时，根因尚未确认。建议在发布前增加首次批量建立定位索引场景的性能回归，检查该查询的执行计划和统计信息，并确认其在 SQL 时限内稳定完成。现有大数据测试允许自动重试，因此测试最终通过不能证明整个过程没有查询超时。

**使用边界**

- 原代码的事件数检查按 `source_key/account_id/conversation_id` 隔离，20000 是单会话累计限制；本次修复将其改为单次解析批次的预算。
- 单轮自身超过配置预算仍会重试/失败。现有集成测试使用 101 个事件和 100 个事件预算验证保护逻辑，不代表已测试单轮 20001 个事件能够成功解析。
- 应用本次代码前需要迁移 `010_round_replay_windows.sql`；缺少它时解析进程无法正常启动。
- 测试针对当前本地工作区代码和本机容器环境；服务器部署状态需要按发布文档验收。
