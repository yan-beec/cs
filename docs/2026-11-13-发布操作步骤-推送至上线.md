## 0. 执行约定

- “本机 PowerShell”的命令在 Windows 上执行；“服务器 Bash”的命令在 `ssh ics` 之后执行。
- 服务器的所有命令都在**同一个 SSH 会话**里执行。`$RUN`、`$EXPECTED_SHA`、`"${C[@]}"` 这些变量只在当前会话有效。断线后按第 12 节恢复，不要重新生成发布目录。
- 第 3.1 步会开启 `set -euo pipefail`：任何命令失败都会直接退出这一层 bash，这是有意设计的，防止带着错误继续往下做。退出后先看清报错原因，再按第 12 节恢复变量。
- 代码块要整块复制，`<<'SQL'`、`<<'PY'`、`<<EOF` 的结尾行也要一起复制。
- `test`、`diff`、`config --quiet` 成功时没有输出，没有输出就是正常结果。

## 5. 第四阶段：进入维护窗口，停止所有写入

**目的：** 迁移会锁表，所以要让所有会写库的服务都停下来，同时保证 Chatwoot 推过来的事件一条都不丢。

时间选择：避开 04:00 的消息清理任务，选一个能容纳第 4.2 步实测耗时再加约 1 小时联调时间的低峰时段。

### 5.1 业务侧准备

1. 通知客服停止操作，期间不要修改快捷回复、黑名单、质检和评分。
2. 按你们现有的方式暂停对外入口（H5、APP、渠道）。确认暂停期间进来的请求会保留或可以重发，并记下暂停的时间。
3. 确认消息清理任务没有在运行：

```bash
pgrep -af '[m]essage_retention|[r]un-message-retention' && echo "有清理任务在跑，先等它结束" || echo "未发现清理任务"
```

**预期：** 输出“未发现清理任务”。

### 5.2 按顺序停服务

**目的：** 先停事件的产生方，再停接收方，最后等 worker 把已经收到的事件处理完再停它。

```bash
docker stop --time 180 chatwoot-sidekiq-1
docker stop --time 120 chatwoot-rails-1
"${C[@]}" stop --timeout 120 ics-agent
"${C[@]}" --profile quality-capture stop --timeout 120 quality-receiver
a_sql -c 'SELECT status,count(*) FROM ops.event_jobs GROUP BY status'
```
