### 如何执行本文的 CLI

- 每次只复制一个“操作”里的代码块，看到它下面的“继续条件”满足后，再执行下一个操作；不要把整章一次性粘贴进终端。
- 标注“本机 PowerShell”的块在 Windows 执行；`ssh ics` 成功后，标注“服务器 Bash”的块才在服务器执行。备份中的 `>` 重定向都在服务器 Bash 内执行，不经过 Windows 转存。
- 多行命令、函数、`while` 循环以及 `<<'SQL'`、`<<'PY'`、`<<EOF` 必须整块复制，结尾的 `SQL`、`PY`、`EOF` 也要复制，不能额外缩进。函数块只定义命令，后续调用时才执行。
- `test`、`[[ ... ]]`、`diff`、`config --quiet` 检查成功时通常没有输出；“无输出”是正常结果。出现报错就停在当前操作，不接着执行后面的启动或迁移。

## 2. 部署方式与必须满足的条件

采用：**冻结发布提交 → 预构建镜像 → 备份恢复与迁移演练 → 维护停流 → 停写后的正式备份 → 同步代码 → 迁移到 021 → 先启消费者 → 历史修正与汇总 → 启动 ICS → 验收 → 开放入口。**

这里不直接使用一条 `release.sh --with-receiver` 完成升级。该脚本会先迁移再构建，并按 receiver、ICS 的顺序启动，不管理 worker；无法体现本次要求的预构建、停流、消费者优先和历史修正检查点。本文复用其 `sync-code.sh` 和 `migrate.sh`，但明确控制顺序。

以下任一项不满足，**不得进入正式迁移**：

- 最终提交、迁移文件、测试记录未冻结，或服务器提交与本次选定的提交号不一致。
- 无法暂停新请求并确认渠道补发/排队机制。单纯停 receiver 会让 Webhook 失败；不能假定 Chatwoot 必然重发。
- 只停止 worker，却让 ICS 继续写分配/在线证据、让 receiver 接收消息。
- 未完成从真实 010 备份恢复到隔离库的迁移和恢复演练；只有空库跑 001–021 不足以代替。
- 备份只有文件大小/目录列表，未验证可恢复；或没有迁移前的业务库备份。
- 磁盘没有容纳备份、新镜像、迁移临时空间/WAL 和恢复副本的余量。
- 业务方不能接受演练测得的维护窗口，或正式窗口可能跨越 04:00 清理任务。

**零遗漏需要入口协调。** 当前检查没有证明外部所有渠道的暂停、持久排队和重发能力。因此维护通知、渠道停流及在途消息确认是执行者必须完成的前置条件；如果做不到，应先建设并验证可靠缓冲/补录方案，不能把在线锁表迁移称为无损升级。

## 7. 第五步：进入维护窗口并停止所有写入者

**目的：** 避免锁表期间归档 Webhook 丢失，取得一致的回退基线。

1. 通知客服退出坐席操作，禁止上传快捷回复、修改排队/黑名单/质检/评分。
2. 暂停 H5、APP、第三方渠道的新请求；由渠道负责人确认暂停期间请求会保留或可重发。保存渠道确认及最后接收时间。
3. 关闭外部与坐席对 ICS、Chatwoot 的访问，仅保留运维访问；按现有网关操作。本文不提供未经核实的网关配置命令。
4. 确认不在 04:00 清理任务运行期间。`pgrep -af 'message_retention|run-message-retention'` 只用于检查，有任务在运行则等其完成或另选窗口。
5. 保持 Rails、Sidekiq 和旧 ICS/receiver/worker 暂时运行，让已有任务完成消息闭环。ICS 处理在途消息时还需要 Rails API，因此不能提前停止 Rails。通过运维访问检查 Sidekiq 管理页队列、重试、定时任务和活动任务。外部入口已暂停，不能在队列仍产生新任务时继续。

**预期：** 队列/重试中涉及本次消息和 Webhook 的任务都已解释并完成，活动任务及 ICS 在途请求为 0。若必须保留定时任务，记录其数量和用途，确保维护期间不会启动 Sidekiq。

检查是否仍有消息清理进程。没有匹配进程时正常显示“未发现”，不会因检查的退出码结束会话：

```bash
if pgrep -af '[m]essage_retention|[r]un-message-retention'; then
  printf '发现清理任务，先等待其完成，不执行下面的停机操作。\n'
else
  printf '未发现消息清理进程。\n'
fi
```

$backupManifest = @(Get-Content -LiteralPath (Join-Path $LocalReleaseDir 'backup.sha256') -ErrorAction Stop)

  shift
  local -a replay_pipeline_status
  "${C[@]}" --profile quality-query run --rm --no-deps -T \
    -v "$HOST_DIR:/app/outputs/handoff-rebuild" \
    quality-worker python -m quality.processing.worker "$@" \

}

```bash

SELECT count(*) AS total_rounds,
       count(f.round_id) FILTER (WHERE f.fact_version=11
         AND (f.messages_until IS NULL OR f.messages_until<CURRENT_TIMESTAMP)) AS current_facts,

         OR f.messages_until>=CURRENT_TIMESTAMP) AS not_current

SELECT count(*) AS pending_facts FROM ops.round_fact_pending;
WITH days AS (
  SELECT generate_series(
    (SELECT (min(started_at) AT TIME ZONE 'Asia/Shanghai')::date FROM ops.round_index),
    (CURRENT_TIMESTAMP AT TIME ZONE 'Asia/Shanghai')::date-1, interval '1 day')::date AS day

LEFT JOIN ops.stat_rollup_days d USING(day)

   OR d.built_at IS NULL OR d.built_at<((d.day+1)::timestamp AT TIME ZONE 'Asia/Shanghai')

| 阶段 | 应对 | 禁止 |
| --- | --- | --- |
| 构建/演练失败，正式停流前 | 保持原服务，修复发布包后重做验证 | 带失败进入生产迁移 |
| 已停流但迁移未开始 | 保留记录；启动原 receiver、worker、ICS，健康后恢复 Rails/Sidekiq及入口 | 无视在途请求和未完成备份 |
| 部分迁移成功 | 保持停流；查询迁移历史，解决根因，重跑同一迁移链；或整套恢复 | 以为脚本失败就已全部回滚 |
| 已迁到 021，新服务失败 | 优先修复可确定的问题；不能及时修好则按下节恢复两库和旧镜像 | 直接套用旧文档“数据库不回退、只退代码” |
| 已恢复真实用户写入 | 先重新停流，备份当前两库并核对新增数据；制定增量保留/重放方案 | 直接把两库覆盖成发布前备份 |
| 历史批次失败 | 保留清单、状态、日志，查明后原批次 `--resume` | 手改状态、删原始事件、重放业务分配接口 |

本文不宣称 010 的全部旧代码已经验证兼容 021。除了 015 删表，019/020/021 和投影语义也变化；保守回退基线是旧镜像 + 010 归档库 + 同一冻结点业务库。当前受限角色和原始证据不能靠简单撤列恢复。

### 13.2 尚未恢复真实用户写入时：完整恢复

**此节是明确的数据覆盖操作，只在决定回退后执行。** 必须确认仍处维护状态、没有真实用户新增写入；受控测试产生的记录列入丢弃清单。已开放入口则不得照抄本节，应先处理增量数据。

```

**操作 145｜检查业务恢复文件（服务器 Bash）**

继续条件：命令成功，无输出。

**目的：** 确认原备份仍完整，保存新结构用于定位。空间不足或失败现场备份失败时停下转移/扩容，不默默跳过。

以下操作会删除并重新创建 `ics_quality` 和 `cs`，**不作用于 Chatwoot 数据库**。执行者再次核对容器名、库名、备份路径后，输入指定确认文本：

**操作 151｜恢复冻结业务备份（服务器 Bash）**

### 13.3 已开放入口后的边界

旧备份不含开放后的新消息归档、分配/排队证据、快捷回复、质检和评分复核。此时恢复备份会造成真实数据倒退；必须先保存当前两库与批次文件，再区分原始不可变证据、业务状态和可重建投影，制定经验证的保留与重放方案。不能仅用 `UPDATE ops.event_jobs`、重新拉一次聊天消息或重跑历史分配去宣称恢复完整性。

## 14. 客户端与业务变化的配套发布

**目的：** 防止服务端升级后，旧客户端继续自动覆盖快捷回复。

- 真实客户端目录为 `D:\project\chatwoot\services\chatwoot\desktop-client`。当前实施记录中的版本仍为 1.4.3，未打包；正式发布应按该项目实际打包配置更新版本、构建、验证安装包并记录 SHA-256，不虚构本仓库能推送它。
- 同一坐席账号的各设备统一升级。旧客户端仍可能自动上传，过渡期间避免新旧版本同时编辑同一账号的快捷回复。
- 登录比较相同则静默；不同仅提示“执行同步/维持当前”，默认、关闭和 Esc 保留当前。编辑只保存本机，只有主动“上传到服务器”才整份覆盖；冲突不自动重试。
- 提前告知统计口径、评分有效性复核和历史人工分类修正。没有排队证据的历史不伪造排队，日/周成功计数不追补历史。
- 历史修正和汇总验收后重新导出离线 HTML；已经发出的旧 HTML 不会自动获得新筛选和新事实。
- 排队总开关首次默认关闭，业务确认配置后再启用；启用时间应单独记录。
